# SC-004 — change-scoped verification timing, measured 2026-10-22

**Criterion as written** (`specs/005-verification-integrity/spec.md`): default verification on a
single-file change completes in **≤25%** of the full-suite time measured by the same command on the
same machine, with both numbers recorded.

**Verdict from the measurement: met from about six checks up, not below.** At 6 checks the ratio is
0.235; at 5 it is 0.273 and at 3 it is 0.444. The criterion names no suite size, so the honest
statement is the one with the floor in it — the numbers are below, and the wording of SC-004 is left
for its owner to amend rather than quietly reinterpreted here.

## Protocol, and why each choice

Every decision below came out of four research rounds against primary sources; the citations are the
reason the protocol is awkward rather than flattering.

| Choice | Why |
|---|---|
| Both configurations run `bin/speckit-verify` | SC-004 says "the same command", so the engine's own cost sits on both sides. Subtracting "startup" would make it a different claim. |
| Nothing subtracted for interpreter startup | A fixed cost removed from one side inflates the ratio precisely where suites are small — the regime where selection looks worst. pyperf/pytest docs make `<testsuite time>` a *separate* metric, not a correction to wall clock. |
| 1 warmup pair discarded | The first run writes `__pycache__`/`.pytest_cache`; pyperf ("usually, skipping the first value is enough") and `hyperfine --warmup` both treat a discard as standard. |
| 7 interleaved pairs (full, changed, full, changed, …) | Running all `full` then all `changed` lets slow drift move one side only. Google Benchmark documents random interleaving for run-to-run variance (≈40% in its own data). |
| Two ratio statistics reported | `median(Aᵢ/Bᵢ)` preserves pairing; `median(A)/median(B)` is a ratio of marginal summaries. They are not interchangeable at small samples, so both appear. |
| Three or more suite sizes | Selection's benefit is a function of suite size, because a fixed session cost does not shrink with the selection. One size cannot support a general claim; a scaling study is the weaker but defensible form. |
| Real per-test computation (~20 ms), not sleeps | With negligible per-test cost the ratio measures process startup instead of selection. |

Sources: [hyperfine](https://github.com/sharkdp/hyperfine), [pyperf warmups](https://pyperf.readthedocs.io/en/latest/run_benchmark.html),
[Google Benchmark interleaving](https://google.github.io/benchmark/random_interleaving.html),
[pytest JUnit XML timing](https://docs.pytest.org/en/stable/_modules/_pytest/junitxml.html),
[Chen & Revels](https://arxiv.org/html/1608.04295v1), [PEP 3147](https://peps.python.org/pep-3147/).

## Numbers

Command, verbatim:

```
python3 evals/measure-sc004.py --pairs 7 --sizes 3,5,6,9,24 \
    --python /tmp/sc004-venv/bin/python --out /tmp/sc004-bracket.json
```

Host: Linux 6.1.102 x86_64, 2 CPUs, load average 0.74 / 0.70 / 0.41 before, 0.70 / 0.69 / 0.41
after; CPython 3.12.3; pytest 9.1.1 in a throwaway venv. 4 tests per module, each doing ~20 ms of
`pbkdf2_hmac` work. Every measured run reported `PASS` — a timing over a failing run would measure
short-circuiting instead.

| checks | full median | changed median | ratio (paired) | ratio (medians) | ratio range | selected | verdict |
|---:|---:|---:|---:|---:|---|---|---|
| 3 | 0.919 s | 0.408 s | **0.444** | 0.443 | 0.419–0.462 | 4/12 | PASS |
| 5 | 1.473 s | 0.402 s | **0.273** | 0.273 | 0.262–0.285 | 4/20 | PASS |
| 6 | 1.741 s | 0.408 s | **0.235** | 0.235 | 0.226–0.247 | 4/24 | PASS |
| 9 | 2.599 s | 0.430 s | **0.166** | 0.166 | 0.154–0.175 | 4/36 | PASS |
| 24 | 6.793 s | 0.428 s | **0.063** | 0.063 | 0.060–0.066 | 4/96 | PASS |

The changed time is flat (0.40–0.43 s) while the full time grows with the suite, which is the whole
mechanism: one check plus the engine's fixed cost. Fitting `ratio ≈ (F + c) / (F + S·c)` with
`F ≈ 0.10 s` (engine) and `c ≈ 0.29 s` (one check, four tests) puts the 25% crossing at
`S ≈ 5.6`, matching the measured bracket between 5 and 6.

## What this does and does not support

- **Supports:** for a suite of ≥6 checks with roughly one check per changed file, default
  verification on a single-file change costs under a quarter of the full suite, and the ratio keeps
  improving with suite size (6.3% at 24 checks).
- **Does not support:** a size-independent claim. A small suite pays the engine and one pytest
  session regardless; below six checks the criterion is missed, and no selector can fix that — the
  fixed cost is not something selection removes.
- **Does not support:** a claim about *this repo's* gate. The kit has no `.specify/verify.json`, so
  `./scripts/verify` still runs the legacy sequence; the measured subject is `bin/speckit-verify` on
  a synthetic project.
- **Limits of the fixture:** uniform per-test cost and one check per module. A real suite with some
  very expensive tests selects even better (the expensive ones are more likely to be skipped); a
  suite of many near-instant tests selects worse. Two CPUs and a synthetic project are not a
  production benchmark.

## Two preconditions discovered while measuring

Both are engine behaviour working as specified, and both are worth knowing before adopting:

1. A project without a `.gitignore` covering `__pycache__/` and `.pytest_cache/` turns every second
   changed run into `INCOMPLETE` — the first run's caches become untracked changed files that no
   check's globs match. That is the intended refusal (an unattributable change must not pass), and
   the fix belongs in the adopter's `.gitignore`.
2. A project with no located spec is `INCOMPLETE` by design (the tally refuses), so a timing fixture
   needs a spec with one evidenced criterion. Real projects have one.
