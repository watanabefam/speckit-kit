# Contract — Commands block and `scripts/verify`

**Consumers:** the installer (writes), `/speckit.tasks` (names the command), the agent (runs it), the
self-gate (asserts).
**Requirements:** FR-005, FR-006, FR-007.

## The `## Commands` managed block

A third managed block in the target project's `AGENTS.md`, written with the same paired-marker,
idempotent mechanism as `SPECKIT-BRIDGE`:

```markdown
<!-- SPECKIT-COMMANDS START -->
## Commands

Detected for this project by `speckit-init`. Run `./scripts/verify` to run test → lint → typecheck.

| Purpose | Command |
| --- | --- |
| install | `npm install` |
| test | `npm test` |
| lint | `npm run lint` |
| typecheck | `npm run typecheck` |
| build | `npm run build` |
| **verify** | `./scripts/verify` |
<!-- SPECKIT-COMMANDS END -->
```

`verify` runs **test → lint → typecheck → build** (install is recorded but not run — installing on every verify is slow and surprising).

When the stack is not detectable, every row reads `unresolved` and the `verify` row is omitted:

```markdown
| Purpose | Command |
| --- | --- |
| test | unresolved — set this by hand or re-run `speckit-init` |
```

## The `scripts/verify` entry point

Generated only when at least one command is detected. Create-if-absent; if it exists, print and do not
overwrite.

```bash
#!/usr/bin/env bash
# Generated by speckit-init. Runs the project's checks in order; stops at the first failure.
set -euo pipefail
run() { printf '\n== %s ==\n' "$1"; shift; "$@"; }
run "test"      npm test
run "lint"      npm run lint
run "typecheck" npm run typecheck
```

**Contract:**

- Runs the recorded commands in the order **test → lint → typecheck → build** (a failing test is the
  most informative first signal).
- Exits **non-zero on the first failure** — `set -e` is the mechanism.
- Prints each step's name before running it, so a failure is attributable.
- Uses no dependency beyond the shell and the project's own tooling.

## How `/speckit.tasks` uses it (FR-007)

A task's **Verification** line names the recorded command, not a guess:

```markdown
- **Verification**: `./scripts/verify` — exits 0, and the new test for FR-004 passes.
```

If the project recorded `unresolved`, the task's Verification line says so and names what the user
must supply, rather than inventing a command.

## Detection signals (a checklist, not a default)

| Ecosystem | Detected from | Commands recorded |
| --- | --- | --- |
| Node | `package.json` scripts (lockfile picks the manager) | `install` (`npm ci` with a lockfile, else `npm install`); `test` / `lint` / `typecheck` / `build` for the scripts that exist |
| Python | `pyproject.toml`, `pytest.ini`, `tox.ini` | `test`; `install` (`uv sync` if `uv.lock`, else `pip install -e .`); `lint` (`ruff`) and `typecheck` (`mypy`) **only when a config file proves the tool is intended** |
| Rust | `Cargo.toml` | `cargo fetch` / `cargo test` / `cargo clippy` / `cargo check` |
| Go | `go.mod` | `go mod download` / `go test ./...` / `go vet ./...` / `go build ./...` |
| Make | `Makefile` with a `test:` target | `make test` |

Detection never invents a command: a tool is claimed only when a config file proves it, and an
unmatched ecosystem falls to `unresolved` (FR-006).

## Acceptance

1. Detectable stack → block written, `scripts/verify` generated, runs in order.
2. Undetectable stack → `unresolved` rows, no `scripts/verify`, one-time prompt printed.
3. `scripts/verify` already exists → printed, not overwritten.
4. Re-running the installer leaves exactly one `SPECKIT-COMMANDS` marker pair (P-004).
